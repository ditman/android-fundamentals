#### [HIGH-001] Hardcoded API Keys in Application Resources

**Severity:** HIGH  
**CWE:** CWE-798 (Use of Hard-coded Credentials)  
**OWASP Mobile:** M9 - Reverse Engineering  
**CVSS Score:** 6.5 (Medium)

**Description:**  
Multiple API keys are hardcoded directly in the application's string resources and manifest file, making them easily extractable through APK decompilation.

**Location:**
- File: `resources/res/values/strings.xml`
  - Line 166: `<string name="facebook_app_id">[REDACTED_FACEBOOK_APP_ID]</string>`
  - Line 167: `<string name="facebook_client_token">[REDACTED_FACEBOOK_CLIENT_TOKEN]</string>`
  - Line 186: `<string name="google_api_key">[REDACTED_GOOGLE_API_KEY_1]</string>`
  - Line 188: `<string name="google_crash_reporting_api_key">[REDACTED_GOOGLE_API_KEY_1]</string>`

- File: `resources/AndroidManifest.xml`
  - Line 309: `<meta-data android:name="com.google.android.geo.API_KEY" android:value="[REDACTED_GOOGLE_MAPS_API_KEY]"/>`

**Technical Analysis:**

These are SDK-specific API keys with the following characteristics:

1. **Facebook SDK Keys:** App ID and Client Token are required for Facebook SDK initialization. While these are considered "public" identifiers in Facebook's security model, their exposure enables:
   - Quota tracking and potential abuse
   - Impersonation in low-security Facebook API calls
   - Analytics data association

2. **Google Maps API Keys:** Two different Google API keys are present:
   - `[REDACTED_GOOGLE_MAPS_API_KEY]` (Maps API)
   - `[REDACTED_GOOGLE_API_KEY_1]` (Crash reporting/general)

   These keys enable:
   - Unauthorized Google Maps API usage
   - Potential quota exhaustion
   - Cost implications for the developer
   - Service disruption if abused

**Risk Assessment:**

While these are SDK keys rather than authentication secrets, their hardcoded presence creates risks:
- **Quota Abuse:** Extracted keys can be used by malicious actors to consume API quotas
- **Cost Impact:** Google Maps API usage can incur significant costs if abused
- **Service Disruption:** Quota exhaustion could disrupt legitimate app functionality
- **Attribution:** API calls made with extracted keys are attributed to Kikoff's account

**Note:** This is standard practice for most Android apps and does not constitute a direct user security risk. However, best practices recommend:
- API key restrictions (domain/package name restrictions in Google Cloud Console)
- Rate limiting
- Monitoring for unusual usage patterns
- Backend proxy for sensitive API calls

**Remediation:**
1. Implement API key restrictions in Google Cloud Console (package name: com.kikoff)
2. Configure Facebook App settings to restrict usage to official app signature
3. Monitor API usage for anomalies
4. Consider backend proxy for high-cost API operations
5. Implement rate limiting on server-side when possible

**CVSS Vector:** CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:L/A:N

#### [MEDIUM-001] WebView Security Configuration

**Severity:** MEDIUM  
**CWE:** CWE-749 (Exposed Dangerous Method or Function)  
**OWASP Mobile:** M7 - Client Code Quality

**Description:**  
The application uses Flutter InAppWebView plugin extensively for displaying web content. While the plugin implements custom WebView clients with security handlers, the configuration and usage patterns should be examined for potential vulnerabilities.

**Location:**
- File: `com/pichillilorenzo/flutter_inappwebview_android/webview/in_app_webview/InAppWebViewClient.java`
- File: `com/pichillilorenzo/flutter_inappwebview_android/webview/JavaScriptBridgeInterface.java`
- Manifest lines 281-288, 645-670: InAppWebView file providers and activities

**Technical Details:**

The InAppWebView plugin provides:
1. **JavaScript Bridge:** Custom interface for Flutter-WebView communication
   - File: `JavaScriptBridgeInterface.java`
   - Risk: Potential for JavaScript injection if input not sanitized

2. **HTTP Authentication Handler:** Custom credential management
   - File: `InAppWebViewClient.java` line 50: `credentialsProposed`
   - Stores URL credentials for reuse

3. **File Access:** FileProvider for sharing files with WebView
   - Authority: `com.kikoff.flutter_inappwebview.fileprovider`
   - Path configuration: `provider_paths.xml`

4. **Chrome Custom Tabs:** Used for OAuth and external links
   - Activities: `ChromeCustomTabsActivity`, `TrustedWebActivity`

**Potential Risks:**

1. **JavaScript Execution:** WebView allows JavaScript execution by default in Flutter InAppWebView
2. **File Access:** File providers could expose app-private files if misconfigured
3. **Mixed Content:** No evidence of strict mixed content policies
4. **SSL Error Handling:** Custom SSL error handlers could be bypassed

**Assessment:**

This is a **standard Flutter plugin** with widespread usage. The security risk depends on:
- How the app configures WebView instances (JavaScript enabled, file access, etc.)
- What domains are loaded in WebViews
- Whether user input is sanitized before being displayed in WebViews

Without access to Flutter Dart code, we cannot fully assess the configuration. The presence of the plugin itself is not a vulnerability, but requires proper usage.

**Recommendations:**

1. Review WebView configurations in Flutter code:
   ```dart
   // Ensure proper settings
   javascriptMode: JavascriptMode.unrestricted, // Evaluate necessity
   allowsInlineMediaPlayback: false,
   mediaPlaybackRequiresUserGesture: true,
   ```

2. Implement Content Security Policy (CSP) headers for loaded web content
3. Validate and sanitize any data passed to WebView from user input
4. Restrict WebView navigation to trusted domains only
5. Disable file access unless absolutely necessary
6. Implement SSL error handling securely (don't ignore cert errors)
